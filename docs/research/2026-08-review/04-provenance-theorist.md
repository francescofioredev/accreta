## F-PT-01: supersedes / superseded_by are inert strings - accreta documents an obsolescence model it does not implement
- Severity: high
- Evidence: MEASURED + REASONED. Grep across both repositories: supersedes appears only in packages/core/src/config.ts:26 (a default string list), config presets (templates/constitution/presets/research.md:22-23, codebase.md:24-25, packages/cli/src/commands.ts:100,126,151), and prose. It appears NOWHERE in drift.ts, lint.ts, page.ts, search.ts, build.ts, or schema.sql. packages/core/src/links.ts:60 stores the field name as an opaque kind (out.push({target, kind: field})) and nothing ever reads it back with meaning. Measured on a 3-page workspace built with buildIndex: SELECT kind, COUNT(*) FROM links GROUP BY kind returns contradicts:1, related:1, superseded_by:1, supersedes:1 - stored, never interpreted. lint() returned {"findings":[],"pagesChecked":3} despite one page being explicitly superseded_by another.
- Where: packages/core/src/links.ts:60, packages/core/src/query/lint.ts:5-13, packages/core/src/config.ts:26
- Failure scenario: A user runs accreta init --preset research and reads templates/constitution/presets/research.md:58-66, "Superseded does not mean deleted... a reader arriving from an old reference needs to land somewhere that tells them it was superseded." They write superseded_by: [[rfc9110]] on the RFC 7231 page. NOTHING TELLS THEM IT WAS SUPERSEDED. lint is silent, drift is silent, search_pages ranks it normally, get_page returns it as an ordinary page. The document is making a promise on the code's behalf that the code never made.
- Falsifiable proposal: Defensible under ADR-0003 ONLY IF THE DOCS STOP IMPLYING INTERPRETATION. Two mutually exclusive exits: (a) KEEP THE CORE VOCABULARY-BLIND, FIX THE PROSE - amend research.md to say plainly that supersedes is an ordinary typed relation and nothing enforces it. Cheap, honest, preserves ADR-0003 exactly. (b) PROMOTE SUPERSESSION TO THE PAGE SCHEMA, NOT THE DOMAIN VOCABULARY - ADR-0003:41-48 already carves out aliases on the rule "a field belongs in the schema if every corpus has it, and in configuration if only some do." Obsolescence passes that test as well as aliases does: every corpus that accumulates over time has superseded entries (RFCs, papers, ADRs, API versions, regulations, internal decisions). The ADR's OWN boundary criterion admits it. Disproof of (b): find a plausible corpus where "this page's subject has been replaced by a successor" is not expressible. My honest read is (b) is stronger and (a) is cheaper; either beats the current state, which claims (b) in the docs and implements neither.
- Cost to verify: 1h for (a); 6-10h for (b) - one schema column, one lint finding kind, one output field in three query functions, tests.
- Confidence: high for the finding (measured, unambiguous); medium on which exit is correct, a product judgement.

## F-PT-02: A contradiction recorded faithfully in markdown is invisible through search_pages, get_page and find_canonical - the interface picks a winner the constitution forbade the author from picking
- Severity: CRITICAL
- Evidence: MEASURED. Built a workspace with knowledge/rfc7231.md (superseded_by: [[rfc9110]]), knowledge/rfc9110.md (supersedes: [[rfc7231]]) and knowledge/conflict-caching.md (type: contradiction, contradicts: [[rfc7231]]), indexed it, and called the exact functions the MCP tools call.
  searchPages(db, {query:"content negotiation"}) returned exactly ONE hit - the SUPERSEDED RFC 7231 page - with fields path, type, title, source, snippet, lastVerifiedRevision. NO CONTRADICTION SIGNAL. The contradiction page did not appear at all, because it does not contain the query terms.
  getPage(db,"rfc7231",config) returned the page. superseded_by is present inside the frontmatter blob, but there is no contradicted_by field, no superseded boolean, and NO TRACE of conflict-caching.md - the contradiction page points AT 7231, so the edge is inbound and appears nowhere in getPage's output.
  findCanonical(db,"RFC 7231 HTTP Semantics and Content",config) returned the SUPERSEDED page as a canonical match with matchedOn:"title" and no qualification - under a tool whose MCP description (packages/mcp-server/src/server.ts:101) reads "Resolve a term to the page that AUTHORITATIVELY defines it."
  The edges DO exist: findRelated(db,"rfc7231",config) returned all three. So the graph is correct and THE DEFAULT READ PATH DOES NOT CONSULT IT.
- Where: packages/core/src/query/search.ts:13-20 (SearchHit has no contradiction field), packages/core/src/query/page.ts:5-14 (PageRecord has no relations), packages/mcp-server/src/tools.ts:29-39, packages/mcp-server/src/server.ts:101
- Failure scenario: An agent asks search_pages("HTTP content negotiation"), gets RFC 7231, calls get_page, reads the body, and writes an answer citing HTTP/1.1 semantics obsoleted in June 2022. EVERY INDIVIDUAL STEP IS CORRECT. The knowledge base contains, on disk, both the supersession edge and a dedicated contradiction page. The agent never sees either, because nothing in the two tools it used mentions them and it had no reason to call a third. Constitution rule 3 violated ONE LEVEL BELOW WHERE THE CONSTITUTION LOOKS - base.md:42-56 binds the AUTHOR, and there is no corresponding obligation on the READER PATH.
- Falsifiable proposal: Add a single vocabulary-independent field, contested, to SearchHit and PageRecord, populated by one query against the already-indexed links table - inbound edges whose kind is in a new config key contested_by_fields (defaulting to [contradicts, superseded_by], i.e. the page's own superseded_by plus inbound contradicts/supersedes). Shape: contested: [{path, kind, title}], empty array when clean. The core still never branches on adapter identity and still enumerates no page types - it reads a config list exactly as extractLinks already does, so ADR-0003 IS PRESERVED. This does NOT re-rank, does NOT filter, does NOT suppress the superseded page: it attaches the fact and lets the consumer decide. That is the difference between SIGNALLING a conflict and RESOLVING one. Disproof: instrument an agent loop and measure how often it calls find_consumers after get_page unprompted. If above ~90%, the signal is redundant and I am wrong. My expectation is near-zero.
- Cost to verify: 4-6h plus the agent-loop measurement. Needs accreta-atlas kb/knowledge/ non-empty, which it is not.
- Confidence: high. The measurement is direct and the output shapes unambiguous.

## F-PT-03: CHANGED, OBSOLETE and CONFLICTING are three different predicates; accreta implements one and its vocabulary implies three
- Severity: high
- Evidence: MEASURED + CITED + REASONED.
  CHANGED - the source bytes moved. detectDrift implements this and only this. It is GENUINELY WELL BUILT - the three-way outcome is a real epistemic distinction most tools collapse, and the comment at drift.ts:96-99 explaining why an empty diff is not drift is the kind of load-bearing remark this project is right to keep.
  OBSOLETE - a successor has replaced the source, whether or not any byte changed. NOT IMPLEMENTED, and UNREACHABLE BY CONSTRUCTION FROM DRIFT. Verified in the atlas corpus: kb/corpus/rfc/rfc7231.txt is byte-frozen (SHA-256 prefix a83d026937f6f792 per PROVENANCE.md:34), so changedSince returns an empty diff forever and drift reports it green forever - CORRECTLY. RFC 9110 obsoleted it in June 2022. grep -c "9110" kb/corpus/rfc/rfc7231.txt returns 0: THE OBSOLETED DOCUMENT CONTAINS NO REFERENCE WHATSOEVER TO ITS SUCCESSOR. The fact lives only in rfc9110.txt line 8 (Obsoletes: 2818, 7230, 7231, ...) and in the RFC Editor's external index.
  CONFLICTING - two sources make incompatible claims. Partially implemented as a page type and a link field, both inert (F-PT-01) and both invisible on the read path (F-PT-02).
  CITED: AGM belief revision (Alchourron, Gardenfors & Makinson, "On the Logic of Theory Change: Partial Meet Contraction and Revision Functions", Journal of Symbolic Logic 50(2):510-530, 1985, https://doi.org/10.2307/2274239) separates CONTRACTION (removing a belief) from REVISION (adding one that conflicts) precisely because they are different operations with different postulates. accreta's superseded_by is closest to contraction-without-deletion. TRANSFER CAVEAT: AGM operates over deductively closed logical theories with a consistency requirement, whereas accreta holds natural-language markdown deliberately allowed to be inconsistent. So AGM gives accreta no ALGORITHM; what it gives is the DISTINCTION - retracting a claim is not deleting a row - which research.md states in prose and the code does not carry.
- Where: packages/core/src/source/drift.ts:96-99, packages/core/src/query/lint.ts:5-13, accreta-atlas/kb/corpus/rfc/PROVENANCE.md:34,51-54
- Failure scenario: The atlas README advertises the frozen corpus as the property that makes drift meaningful in CI, and it is right. But that same property GUARANTEES that the single most important epistemic fact about RFC 7231 - that it has been obsolete since 2022 - can never surface. A user sees green and concludes the KB is current. It is current with respect to BYTES and stale with respect to STANDING. The test bed chosen to prove drift works is simultaneously the sharpest demonstration of what drift cannot see.
- Falsifiable proposal: This is a GAP, NOT AN ACCEPTABLE SCOPE BOUNDARY, and the reason is that ACCRETA ALREADY SPENT THE VOCABULARY. A tool that never mentioned supersession would have a clean boundary. A tool shipping supersedes, superseded_by and a contradiction page type in its default config and its constitution HAS ALREADY TOLD THE USER IT HANDLES OBSOLESCENCE. Scope boundaries are only honest when declared; this one is contradicted by the product's own presets. The minimal honest fix does NOT require accreta to learn about RFCs: one distinction in lint - a page whose superseded_by resolves to an existing page, and which is ITSELF still being returned as canonical, is a lint finding (superseded-page-is-canonical). Checkable purely from the link graph, no adapter knowledge, no inference. Disproof: if users of the research preset overwhelmingly never populate superseded_by, the field is decoration and the honest fix is deletion, not implementation.
- Cost to verify: 3h for the lint finding and tests. The survey is blocked on adoption.
- Confidence: high on the three-way distinction and the RFC 7231 measurement; medium on "gap not boundary", an argued judgement - though "already spent the vocabulary" is what moves me off the fence.

## F-PT-04: Obsolescence has four possible authorities; only the two weakest are expressible today, and the machine-readable one points the wrong way
- Severity: medium
- Evidence: MEASURED + CITED. Ranked by how much the system should trust them:
  1. THE PUBLISHER DECLARES IT, IN THE SUCCESSOR DOCUMENT. Strongest: the issuing authority speaking, in-band, a recorded fact rather than an inference. Machine-readable in the atlas corpus - the header line survives vendoring intact: rfc9110.txt "Obsoletes: 2818, 7230, 7231, 7232, 7233, 7235, 7538, 7615, 7694"; rfc9111.txt "Obsoletes: 7234"; rfc8446.txt "Obsoletes: 5077, 5246, 6961"; rfc7231.txt "Obsoletes: 2616". Fixed-column header, trivially extractable.
     THE CRITICAL ASYMMETRY: this authority is only ever expressed FORWARD. A document declares what it obsoletes; it can NEVER declare what obsoletes it, because that has not been written yet. grep -c "9110" rfc7231.txt = 0. So the obsolescence of a source is knowable ONLY FROM A DOCUMENT THAT IS NOT THAT SOURCE - which means PER-SOURCE DRIFT DETECTION CAN NEVER FIND IT, no matter how good the adapter is. A STRUCTURAL RESULT, not an implementation gap.
  2. AN EXTERNAL REGISTRY DECLARES IT. The RFC Editor's index carries "Obsoleted by" as a first-class field. Strong but out-of-band: needs a network fetch or a vendored snapshot, and the snapshot then has its own drift problem - a genuinely interesting recursion, since the registry is exactly the kind of source that DOES change while the documents do not.
  3. THE USER DECLARES IT in configuration or frontmatter. Weaker than a publisher but LEGITIMATE under the constitution because declarative: a human asserted it, recorded and attributable. This is where accreta's superseded_by sits, and it is the right home for it.
  4. THE AGENT INFERS IT FROM READING. Precisely the inference the constitution forbids - the agent deciding, on its own authority, that one source replaced another. Must never be the SOLE basis for a supersession edge. The softer legitimate version: an agent may PROPOSE an edge from having read "Obsoletes: 7231" in RFC 9110's header, because then it is TRANSCRIBING authority 1, not exercising authority 4. The distinction is whether a citation can be attached.
- Where: design-level; corpus evidence at accreta-atlas/kb/corpus/rfc/rfc9110.txt:8, rfc7231.txt:9, PROVENANCE.md:34-39
- Failure scenario: Today all four authorities collapse into one indistinguishable string. A superseded_by edge transcribed from RFC 9110's own header (authority 1, citable, near-certain) and one an agent guessed because two pages looked similar (authority 4, forbidden) are BYTE-IDENTICAL in frontmatter. A reviewer cannot tell which is which, and neither can lint. The forbidden inference is not prevented - it is merely indistinguishable from the permitted transcription.
- Falsifiable proposal: Require supersession edges to carry provenance like every other non-trivial claim, using the mechanism accreta already has. Instead of a bare superseded_by, the constitution should require the assertion be citable in the body ("RFC 7231 was obsoleted by RFC 9110.[^obs]" / "[^obs]: rfc-http @ a83d026 - rfc9110.txt#L8"), and lint should report a superseded_by edge on a page whose body carries no citation as uncited-supersession. Costs no new frontmatter vocabulary, reuses constitution rule 1 verbatim, and makes authority 4 VISIBLE by making it the only case that cannot produce a line number. It cannot make authority 4 impossible - nothing can - but it converts an undetectable violation into a detectable one, which is this project's whole method. Disproof: if supersession claims routinely have no citable line anywhere in either document (plausible for corpora with no formal obsolescence convention), the rule generates noise rather than signal and should be a warning.
- Cost to verify: 3-4h; NEEDS A BODY-CITATION PARSER, WHICH DOES NOT EXIST IN CORE - page.ts stores body as an opaque string and nothing parses footnotes. A real prerequisite, not a detail.
- Confidence: high on the four-way ranking and the forward-only asymmetry (both measured); medium on the lint rule, which depends on infrastructure not built.

## F-PT-05: An authority model that does not pick winners - authority attaches to a source at a revision, for a scope, and is never applied to filter
- Severity: medium
- Evidence: CITED + REASONED. Authority cannot attach to a CLAIM, because accreta does not index claims - pages_fts indexes title, aliases and body as text and there is no claim-level object. It should not attach to a PAGE, because a page is accreta's own artifact, not the source's - making a page authoritative would let the knowledge base confer authority ON ITSELF, which is circular. That leaves A SOURCE, AT A REVISION, WITHIN A SCOPE: RFC 9110 is authoritative over 7231 FOR HTTP SEMANTICS, and says nothing about caching, which moved to RFC 9111.
  Concretely, in accreta.config.yaml - declarative, user-written, never inferred:
    authority:
      - scope: "http-semantics"
        prefer: rfc-http/rfc9110.txt
        over: [rfc-http/rfc7231.txt]
        because: "rfc9110.txt#L8 Obsoletes: 7231"
  The because field is LOAD-BEARING and should be REQUIRED: an authority declaration without a citation is an opinion, and rule 1 already says opinions do not go in the knowledge base. Requiring it also blocks the lazy global "prefer newer" rule, which is exactly the silent ranking function the constitution forbids.
  CITED: Dung, "On the acceptability of arguments and its fundamental role in nonmonotonic reasoning, logic programming and n-person games", Artificial Intelligence 77(2):321-357, 1995, https://doi.org/10.1016/0004-3702(94)00041-X - defines a framework as a pair (A,R), arguments and an attack relation, and THE FRAMEWORK IS A REPRESENTATION ENTIRELY SEPARATE FROM THE SEMANTICS (preferred, grounded, stable extensions) one may optionally compute over it. The framework REPRESENTS the conflict; computing an extension RESOLVES it. accreta should build the (A,R) and NEVER COMPUTE AN EXTENSION. That is exactly the architectural line the constitution draws, and it is reassuring that a 1995 result draws it in the same place. TRANSFER CAVEAT: Dung's arguments are formal objects with a decidable attack relation, accreta's are prose pages whose "attack" is an editorial judgement - so accreta gets the STRUCTURE (represent, don't resolve), not the SEMANTICS.
  ADVERSARIAL READ AS INSTRUCTED: TruthFinder (Yin, Han & Yu, "Truth Discovery with Multiple Conflicting Information Providers on the Web", IEEE TKDE 20(6):796-808, 2008, https://doi.org/10.1109/TKDE.2008.76) iteratively co-estimates website trustworthiness and fact confidence and outputs a single winner per query. IT DOES NOT APPLY, AND NOT OUT OF SQUEAMISHNESS ABOUT RANKING. Three required conditions are absent: (i) it needs many redundant providers asserting the SAME attribute, whereas accreta's canonical case is exactly two documents, one of which formally replaced the other; (ii) its trust signal is derived from AGREEMENT FREQUENCY, which is inference - the forbidden authority 4, industrialised; (iii) its output is a point estimate that DISCARDS the disagreement, which is the artifact accreta exists to preserve. Where it DOES transfer: its insight that source trust and claim confidence are distinct quantities is right, and supports keeping authority attached to sources rather than claims.
- Where: design-level; packages/core/src/config.ts:12-21
- Failure scenario: Without a declarative authority model, a user with a genuine editorial position - "in this knowledge base, RFC 9110 governs HTTP semantics" - has nowhere to record it, so they encode it the only way available: by writing the RFC 7231 page more weakly, or DELETING it. Both worse. Deletion is what research.md:65 explicitly warns against, and the tool currently gives the user NO SUPPORTED ALTERNATIVE TO THE THING THE CONSTITUTION TELLS THEM NOT TO DO.
- Falsifiable proposal: Add the authority block, and constrain its use to exactly one thing: ANNOTATION. It may populate the contested field from F-PT-02 and it may sort WITHIN an already-returned result set. It may never remove a result, never filter, and never change which pages are returned - enforced by a test asserting result-set MEMBERSHIP is identical with and without any authority block present. THAT TEST IS THE FALSIFICATION: if anyone ever needs to relax it, the feature has become a ranking function that resolves contradictions and should be reverted.
- Cost to verify: 8-12h. Depends on F-PT-02's contested field existing first - without a channel to surface authority through, the config block would be as inert as supersedes is today, which would be the same mistake twice.
- Confidence: medium. Literature grounding solid and verified, but a design proposal I could not test against real users; the scoping question ("http-semantics" as a free string) may not survive a second corpus.

## F-PT-06: last_verified_revision records that a check happened, not who made it or how - and PROV-O's Entity/Activity/Agent split is the distinction accreta is missing
- Severity: high
- Evidence: CITED + MEASURED. W3C PROV-O (W3C Recommendation, 30 April 2013, https://www.w3.org/TR/prov-o/) separates three things accreta collapses into one string. prov:Entity is "a physical, digital, conceptual, or other kind of thing with some fixed aspects" - accreta's page and source. prov:Activity is "something that occurs over a period of time and acts upon or with entities" - THE VERIFICATION EVENT, which accreta has no representation of at all. prov:Agent is "something that bears some form of responsibility for an activity taking place" - the model or human that did the verifying, likewise absent. prov:wasAssociatedWith links Activity to Agent; prov:wasAttributedTo ascribes Entity to Agent.
  MEASURED: pages has last_verified_revision TEXT (schema.sql:18) and nothing else about verification. PageRecord exposes lastVerifiedRevision: string|null. updateVerifiedRevisionTool (tools.ts:144-188) writes exactly one frontmatter field - no timestamp, no actor, no method. A verification by a frontier model that read 300 lines carefully and one by a cheap model that skimmed the filename produce BYTE-IDENTICAL FRONTMATTER.
  This is the gap base.md:144-146 names as "the single most damaging thing you can do here" - and the system has no way to tell it happened, BY ITS OWN DESIGN.
  WHERE ACCRETA IS GENUINELY DIFFERENT FROM PROV, AND RIGHT TO BE: PROV models provenance of DATA ARTIFACTS THROUGH WORKFLOWS, assuming an execution environment that OBSERVES activities as they run. accreta's verification is an act of READING AND JUDGING, performed by an agent that could simply lie about it. No vocabulary fixes that. Adopting PROV's RDF wholesale would be a large dependency for a project whose substance is markdown in git. THE USEFUL IMPORT IS ONE DISTINCTION, NOT A SERIALIZATION: verification is an Activity with an Agent, not an attribute of an Entity.
  ON TRUST DECAY: a verification ages even when the source does not. The atlas corpus proves it - RFC 7231's bytes are frozen forever, so drift reports it current forever, while the world moved in June 2022. "Verified at revision R" and "verified recently" are different assurances, and accreta offers only the first while its CI green implies the second. Useful asymmetry with PROV: prov:invalidatedAtTime marks when an entity ENDED, a fact about the SOURCE; what accreta needs is when a VERIFICATION stopped being trustworthy, a fact about the ACTIVITY. PROV can express it because it models the activity as an object; accreta cannot, because it does not.
- Where: packages/core/src/index-db/schema.sql:18, packages/core/src/query/page.ts:11, packages/mcp-server/src/tools.ts:178
- Failure scenario: Two agents maintain a KB over six months. One re-reads sources properly; the other, under context pressure, bumps last_verified_revision to silence a stale report - the exact failure base.md:144-146 warns about. After six months lint reports zero findings, drift reports zero stale pages, CI is green. THERE IS NO QUERY, IN ANY TOOL, THAT DISTINGUISHES THE HONEST HALF FROM THE DISHONEST HALF. The KB is now confidently wrong and reads as authoritative - the failure base.md:55-57 names as worse than saying nothing. Worse still, the green CI is EVIDENCE to the user that this did not happen.
- Falsifiable proposal: The cheapest honest version adds no new subsystem and no RDF - three optional frontmatter fields written by the one tool that already exists: last_verified_revision, last_verified_at (when the Activity occurred), last_verified_by (the Agent, self-reported). updateVerifiedRevisionTool writes all three (setFrontmatterField takes a field name, so it generalises for free). Then lint gains verification-unattributed for a page with a revision but no _at/_by.
  BE HONEST ABOUT WHAT THIS BUYS, because overclaiming would repeat the project's characteristic failure: last_verified_by is SELF-REPORTED AND TRIVIALLY FORGEABLE. It does not make verification trustworthy. What it does is make the POPULATION AUDITABLE - a reviewer can ask "which pages were verified by which agent, in which session, and did that session actually read the source?" and cross-reference sessions/, which the atlas keeps one transcript per ingest batch in. That turns an unanswerable question into a checkable one. last_verified_at additionally makes trust decay expressible: accreta drift --max-age 180d could report pages whose VERIFICATION is old even where the source is frozen - a fourth outcome, and THE ONLY ONE THAT WOULD EVER FIRE ON THE ATLAS RFC CORPUS.
  Disproof: if agents populate last_verified_by with a constant or omit it whenever optional, the field is theatre and should be either enforced or dropped.
- Cost to verify: 4-6h for fields, lint rule and tests; 3-4 more for --max-age.
- Confidence: high that the gap is real and matters; medium on the specific fix, since self-reported attribution is weak.

## F-PT-07: CREDIT - the three-way drift outcome, the confirm-token write gate, and broken_links are each correct in ways a reviewer would be tempted to attack
- Severity: low
- Evidence: MEASURED + REASONED. Three pieces are right, and each looks like over-engineering until examined.
  THE THREE-WAY DRIFT OUTCOME (drift.ts:4-25). stale/unverifiable/unresolvable reads as needless taxonomy - most tools return a boolean. It is not: unverifiable ("no revision recorded") and unresolvable ("a revision the source cannot place") are genuinely different epistemic states, and collapsing either would lose the distinction between NOT CHECKED and CHECKED AGAINST SOMETHING THAT NO LONGER EXISTS. The atlas found a real bug precisely because these are distinct (findings.md:36-51: a bare all-digit YAML revision silently became null, turning an unresolvable fixture into an unverifiable one - the fixture would have passed FOR THE WRONG REASON). A boolean would have hidden that permanently.
  THE CONFIRM_TOKEN (tools.ts:114-127). A hash over path\0revision\0currentValue requiring a dry run before any write looks like friction on a single-field edit. The comment explains why - "a plain confirm: true flag would let a model skip straight to writing" - and it is correct: a token that cannot be produced without having performed the dry run, and that becomes invalid if the page changed underneath, is meaningfully different from a boolean an autoregressive model will emit because the schema mentions it. Given F-PT-06 - that a false verification is undetectable forever - making this one tool difficult is the RIGHT ALLOCATION OF FRICTION.
  BROKEN_LINKS AS A TABLE (schema.sql:57-66). Storing links that failed to resolve looks like keeping garbage. The comment names the incident - "silently discarding it is how the '..' defect stayed invisible" - and lint.ts:34-41 states the principle correctly: "a link that does not resolve looks exactly like a page with fewer relations."
  I note also that packages/core genuinely does not branch on adapter identity - detectDrift asks only revision() and changedSince(), and the comment states the invariant AND ITS FALSIFICATION CONDITION ("if it ever needs to, the interface is missing something"). My findings deliberately do not propose breaking this: the contested field in F-PT-02 reads the LINK GRAPH, not the adapter.
- Falsifiable proposal: Keep them, and keep the comments. Disproof: if the unresolvable outcome never fires in practice, the taxonomy is over-built. The atlas fixtures/unresolvable canary exists to make it fire, so this is already instrumented.
- Confidence: high.

## F-PT-08: A logically impossible supersession state passes lint clean
- Severity: medium
- Evidence: MEASURED. Built a two-page KB where a.md declares BOTH supersedes: [[b]] AND superseded_by: [[b]], and b.md the mirror - A replaced B and B replaced A, simultaneously, in both directions. lint(db,config) returned {"findings":[],"pagesChecked":2}. ZERO FINDINGS. Follows directly from F-PT-01 - lint's five kinds are about links resolving, types being known, and provenance being present, none violated here. Every link resolves. Both pages have canonical_source and last_verified_revision. The KB is, by every check accreta performs, IN PERFECT HEALTH while asserting a contradiction no reader could act on.
- Where: packages/core/src/query/lint.ts:5-13, :78-110
- Failure scenario: An agent ingesting a corpus with a complex revision history - TLS, where rfc8446.txt:9 declares Obsoletes: 5077, 5246, 6961 while also carrying Updates: 5705, 6066 - writes a plausible-looking but inconsistent set of edges across several sessions. Each session's edit is locally reasonable. Nothing ever reports the global inconsistency. Six months later the supersession graph is unusable and there is no signal indicating when it broke.
- Falsifiable proposal: One lint finding, inconsistent-supersession, firing on (a) a mutual supersedes pair, (b) a cycle in the supersedes edge set, (c) a supersedes edge without the reciprocal superseded_by on the target, where both pages exist. All three are pure graph properties over the links table, one query plus a traversal - no adapter knowledge, no page-type knowledge, no inference. (c) will fire most and is most useful: it catches the half-written edge, the realistic failure. If F-PT-01 exit (a) is chosen, this must be driven by a config key naming the pair (supersession_fields) rather than hardcoding names, keeping ADR-0003 intact. Disproof: if real KBs legitimately contain supersedes cycles - plausible if someone uses the field for "revises" in a corpus with circular revision histories - then (b) is wrong and only (a) and (c) survive. I could not find such a corpus but did not look hard.
- Cost to verify: 2-3h including tests.
- Confidence: high on the measurement; medium on rule (b).

## Experiment cards
1. DOES A CONTRADICTION REACH THE AGENT? Populate atlas kb/knowledge/ with RFC 7231 (superseded_by), RFC 9110 (supersedes), and a type:contradiction page on caching citing rfc9111.txt#L173. Run the MCP server read-only. Ask 20 questions whose correct answer depends on knowing 7231 is obsolete, with NO hint that supersession exists. Record which tools were called and whether the final answer mentions the supersession. Apply the contested patch; repeat identically. Metric: proportion of trials whose FINAL ANSWER names the supersession - that and not tool-call counts, because the failure that matters is the USER READING AN ANSWER that omits a fact the KB contains. Falsification: baseline >=50%, or after-patch <90%; or if agents call find_consumers reflexively after every get_page, the signal is redundant. Hypothesis: under 20% baseline, over 90% patched. Cost ~4h plus 40 trials. Not measured: whether agents WRITING pages record contradictions faithfully - this tests only the read path. Also n=20 gives a 20% point estimate a 95% CI of roughly 6-44%, wide enough that only a large effect is detectable; deliberate, since the hypothesised effect is large, but a null result would need more trials, not a conclusion.
2. DOES VERIFICATION ATTESTATION SURVIVE CONTACT WITH AN AGENT? Patch updateVerifiedRevisionTool to write all three fields. Run one full ingest batch following kb/AGENTS.md. Cross-reference every page's last_verified_by against the session transcript: for each page claiming verification, check whether the transcript shows the source file ACTUALLY BEING READ in that session. Metric: proportion of verification claims corroborated by a matching read - the only available external check on a self-reported field, the difference between an attestation and a decoration. Falsification: >=95% corroboration means unattested verification is not a real problem and F-PT-06 is over-stated; below ~70% means the attestation is necessary AND insufficient, and the honest response is to make the tool the only path rather than to trust the field. Cost ~6h. Not measured: adversarial behaviour - this measures the cooperative case, the optimistic bound.

## What I could not establish
- Whether the contested field would CHANGE agent behaviour. F-PT-02 measures conclusively that the INTERFACE omits the signal; it does not measure that adding it changes answers. Blocked on atlas kb/knowledge/ being non-empty. I designed the measurement rather than guessing the number.
- Whether real users populate superseded_by at all. F-PT-01's exit (a) vs (b) turns on this, and accreta is at 0.1.2 with one downstream test bed whose KB is empty by design. Answerable only by adoption; until then the argument for (b) rests on ADR-0003's own corpus-generality criterion rather than usage data, and I flag that as argued rather than measured.
- Whether supersedes cycles are ever legitimate. F-PT-08's rule (b) assumes not. I did not search exhaustively, and "I did not find one" is weak evidence for "none exists".
- The right scoping granularity for authority declarations. Cannot be settled against one corpus. Needs a second corpus with a different supersession shape - the codebase preset would be the natural test, and findings.md:86-87 records it has no demo anywhere.
- Whether verification decay has a defensible default half-life. I deliberately name NO default. Any number I picked would be invention. The honest position is that the flag should exist with no default, requiring the user to declare a decay period - the declarative-not-inferred principle applied to time.
- I did NOT evaluate ADR-0001, 0002, 0004 or 0005. Open per my brief but not load-bearing for Q6/Q7. I read ADR-0003 because supersession tests it directly, and my findings are deliberately constructed to preserve it: every proposal reads a config-declared field list or the link graph, and none teaches the core a page type or an adapter identity.
